# Сервис бронирования футбольных полей — Backlog (JIRA)

Структура: **Epic → User Story → Задачи (Tasks)**
Каждая история содержит критерии приёмки (Acceptance Criteria) - условия, при которых задачу можно считать выполненной.

---

## EPIC 1: Поиск и бронирование слота

### Story 1.1: Поиск доступных слотов
**Как** игрок, **я хочу** увидеть свободные слоты по выбранным дате, времени и типу поля, **чтобы** быстро найти подходящий вариант для игры.

**Acceptance Criteria:**
- Пользователь может отфильтровать слоты по: комплекс, дата, тип поля (5x5/8x8/11x11), диапазон времени
- Система показывает только реально свободные слоты (без учёта уже забронированных или заблокированных администратором)
- Если по заданным фильтрам ничего не найдено - система предлагает ближайшие альтернативы (другое время в тот же день / соседний комплекс)
- Время отклика - не более 2 секунд (см. NFR-1)

**Задачи:**
- [ ] BOOK-101: Спроектировать API-эндпоинт GET /fields/available-slots
- [ ] BOOK-102: Реализовать логику фильтрации слотов по параметрам
- [ ] BOOK-103: Реализовать подбор альтернативных слотов при отсутствии совпадений
- [ ] BOOK-104: Написать тесты на граничные случаи (нет полей вообще, все занято)

### Story 1.2: Разовое бронирование слота
**Как** игрок, **я хочу** забронировать выбранный слот и оплатить его, **чтобы** гарантированно получить поле на нужное время.

**Acceptance Criteria:**
- При выборе слота система резервирует его на 15 минут (см. FR-3)
- Если оплата не поступила за 15 минут - слот автоматически освобождается (см. FR-4)
- Два пользователя не могут одновременно забронировать один и тот же слот (см. NFR-2)
- После успешной оплаты пользователь получает подтверждение (push/SMS) в течение 1 минуты (см. NFR-3)

**Задачи:**
- [ ] BOOK-105: Спроектировать API-эндпоинт POST /bookings
- [ ] BOOK-106: Реализовать временную блокировку слота (soft lock, 15 минут)
- [ ] BOOK-107: Настроить фоновую задачу освобождения слота при истечении таймера
- [ ] BOOK-108: Интегрироваться с Payment Service
- [ ] BOOK-109: Publish событие booking.confirmed в Kafka после успешной оплаты
- [ ] BOOK-110: Продумать и реализовать защиту от race condition при одновременном бронировании

## EPIC 2: Регулярные бронирования (для команд)

### Story 2.1: Создание регулярной брони
**Как** капитан команды, **я хочу** забронировать поле на несколько недель вперёд по расписанию (например, каждый вторник), **чтобы** не бронировать вручную каждую неделю.

**Acceptance Criteria:**
- Капитан указывает день недели, время и период повторения (см. UC-2)
- Система проверяет доступность на все даты серии
- Если хотя бы одна дата занята - пользователю предлагается выбор: пропустить дату или изменить время для всей серии
- Открытый вопрос из требований (оплата целиком/помесячно) - уточнить с заказчиком до реализации

**Задачи:**
- [ ] BOOK-201: Спроектировать модель данных для серии бронирований (recurring_booking)
- [ ] BOOK-202: Реализовать проверку доступности на весь период серии
- [ ] BOOK-203: Реализовать UI/API выбора действия при конфликте дат
- [ ] BOOK-204: Уточнить с заказчиком схему оплаты серии (блокирующий вопрос)

### Story 2.2: Приглашение игроков в команду
**Как** капитан, **я хочу** пригласить других игроков в свою бронь по ссылке, **чтобы** собрать команду на игру.

**Acceptance Criteria:**
- Капитан может сгенерировать ссылку-приглашение на конкретную бронь
- Приглашённый пользователь видит детали брони (время, поле, состав) до подтверждения участия
- Список участников виден капитану в деталях брони

**Задачи:**
- [ ] BOOK-205: Спроектировать API для генерации invite-ссылки
- [ ] BOOK-206: Реализовать страницу присоединения к брони по ссылке
- [ ] BOOK-207: Добавить сущность "участник брони" в модель данных

## EPIC 3: Отмена и возврат средств

### Story 3.1: Отмена бронирования
**Как** игрок, **я хочу** отменить бронь, **чтобы** не платить за игру, которая не состоится.

**Acceptance Criteria:**
- При отмене за 24+ часа до начала - полный возврат средств (см. FR-8)
- При отмене менее чем за 24 часа - возврат 50% (правило зафиксировано как условное, требует подтверждения заказчика)
- После отмены слот немедленно становится доступен другим пользователям
- Пользователь получает уведомление о статусе возврата

**Задачи:**
- [ ] BOOK-301: Спроектировать API-эндпоинт DELETE /bookings/{id}
- [ ] BOOK-302: Реализовать расчёт суммы возврата по правилам
- [ ] BOOK-303: Интегрироваться с Payment Service для возврата средств
- [ ] BOOK-304: Publish событие booking.cancelled в Kafka (для уведомлений и освобождения слота)

## EPIC 4: Администрирование расписания

### Story 4.1: Управление слотами и ценами
**Как** администратор комплекса, **я хочу** блокировать слоты и настраивать цены, **чтобы** учитывать техобслуживание полей и спрос по времени.

**Acceptance Criteria:**
- Администратор может вручную заблокировать слот с указанием причины (см. FR-9)
- Администратор может задать правила ценообразования: тип поля + день недели + диапазон времени → цена (см. FR-5)
- Изменение цены не влияет на уже подтверждённые брони (только на новые)

**Задачи:**
- [ ] BOOK-401: Спроектировать модель данных "Правило цены" (pricing_rule)
- [ ] BOOK-402: Реализовать API управления блокировками слотов
- [ ] BOOK-403: Реализовать API управления правилами цен (CRUD)
- [ ] BOOK-404: Написать тесты на пересекающиеся/конфликтующие правила цен

## EPIC 5: Уведомления

### Story 5.1: Уведомления о бронировании
**Как** пользователь, **я хочу** получать уведомления о статусе брони, **чтобы** быть в курсе подтверждения, напоминаний и отмен.

**Acceptance Criteria:**
- Уведомление отправляется при: подтверждении брони, за 2 часа до игры, при отмене (см. FR-6)
- Уведомления доставляются не позднее 1 минуты после события (см. NFR-3)
- Notification Service подписан на события booking.confirmed и booking.cancelled из Kafka

**Задачи:**
- [ ] BOOK-501: Спроектировать consumer для топика booking-events в Kafka
- [ ] BOOK-502: Реализовать шаблоны уведомлений (подтверждение/напоминание/отмена)
- [ ] BOOK-503: Настроить отложенную отправку напоминания (за 2 часа до слота)
- [ ] BOOK-504: Интегрироваться с провайдером push/SMS

## EPIC 6: Аналитика (для владельца сети)

### Story 6.1: Дашборд загрузки и выручки
**Как** владелец сети, **я хочу** видеть загрузку полей и выручку, **чтобы** принимать решения о ценах и расписании.

**Acceptance Criteria:**
- Доступна фильтрация по комплексу, полю, периоду (см. UC-5)
- Отображается: % загрузки по дням недели, выручка за период, топ клиентов по количеству броней
- Данные обновляются не реже раза в сутки (можно уточнить у заказчика, нужен ли real-time)

**Задачи:**
- [ ] BOOK-601: Написать SQL-запросы для агрегации метрик (загрузка, выручка, топ клиентов)
- [ ] BOOK-602: Спроектировать API-эндпоинт для дашборда
- [ ] BOOK-603: Согласовать с заказчиком частоту обновления данных

## Приоритизация Backlog (порядок реализации)

1. Epic 1 (Поиск и бронирование) - ядро продукта, без него ничего не работает
2. Epic 5 (Уведомления) - критично для доверия пользователей
3. Epic 3 (Отмена) - обязательная часть базового флоу
4. Epic 4 (Администрирование) - нужно для работы бизнеса
5. Epic 2 (Регулярные брони) - расширение базового функционала
6. Epic 6 (Аналитика) - не блокирует запуск, можно добавить позже

*Примечание: такая приоритизация — пример MoSCoW-подхода (Must have / Should have), где Epic 1, 3, 5 — Must have для MVP, а Epic 2, 4, 6 — Should/Could have.*
