# Kafka-интеграции - Сервис бронирования футбольных полей

**Статус:** Черновик
**Связанные задачи:** BOOK-109, BOOK-304, BOOK-501, BOOK-502 (см. Backlog)

---

## 1. Обзор

Асинхронное взаимодействие между сервисами реализуется через Apache Kafka.
Booking Service публикует события о смене статуса брони, Notify Service подписан
на эти события и рассылает пользователям push/SMS-уведомления.

**Почему асинхронно, а не через REST:** отправка уведомления - это побочный эффект,
который не должен блокировать основной процесс бронирования или отмены (см. пояснение
в Sequence Diagram). Если Notify Service временно недоступен, событие остаётся в топике
и будет обработано позже - данные не теряются.

---

## 2. Топик: `booking-events`

| Параметр | Значение |
|---|---|
| Название топика | `booking-events` |
| Ключ партиционирования | `bookingId` |
| Количество партиций | 3 (условно, для учебного проекта) |
| Гарантия доставки | At-least-once (см. раздел 5) |

**Почему партиционируем именно по `bookingId`:** все события одной и той же брони
должны обрабатываться строго по порядку (например, нельзя, чтобы `booking.cancelled`
обработалось раньше `booking.confirmed`). Kafka гарантирует порядок сообщений только
*внутри одной партиции* - поэтому события с одинаковым ключом всегда попадают в одну
и ту же партицию и не могут "обогнать" друг друга.

---

## 3. Типы событий (Event Schema)

### 3.1 `booking.confirmed`

Публикуется Booking Service после успешной оплаты (см. Sequence Diagram UC-1,
Диаграмму состояний: переход Создана → Подтверждена).

```json
{
  "eventType": "booking.confirmed",
  "bookingId": "booking_78341",
  "userId": "user_1001",
  "fieldId": "field_204",
  "slotDate": "2026-09-05",
  "slotTime": "20:00",
  "timestamp": "2026-09-01T14:32:10Z"
}
```

| Поле | Тип | Обязательное | Комментарий |
|---|---|---|---|
| eventType | string | да | Фиксированное значение, по нему консьюмер решает, как обработать событие |
| bookingId | string | да | Используется как ключ партиционирования |
| userId | string | да | Нужен Notify Service, чтобы понять, кому слать уведомление |
| fieldId | string | да | Для формирования текста уведомления ("Поле №3, Complex Sochi") |
| slotDate, slotTime | string | да | Для текста напоминания за 2 часа (см. BOOK-503) |
| timestamp | string (ISO 8601) | да | Время события — нужно для отладки и построения метрик |

### 3.2 `booking.cancelled`

Публикуется Booking Service после отмены брони (см. Sequence Diagram UC-3,
Диаграмму состояний: переход Подтверждена → Отменена).

```json
{
  "eventType": "booking.cancelled",
  "bookingId": "booking_78341",
  "userId": "user_1001",
  "refundPercent": 100,
  "refundAmount": 2500,
  "timestamp": "2026-09-01T15:10:00Z"
}
```

| Поле | Тип | Обязательное | Комментарий |
|---|---|---|---|
| refundPercent | integer | да | 100 или 50 - см. FR-8. Нужно, чтобы уведомление сообщало точную сумму возврата |
| refundAmount | number | да | Итоговая сумма в рублях, чтобы не заставлять Notify Service пересчитывать её самостоятельно |

*Остальные поля — как в `booking.confirmed`.*

## 4. Producers / Consumers

| Сервис | Роль | Топик | Комментарий |
|---|---|---|---|
| Booking Service | Producer | `booking-events` | Публикует оба типа событий |
| Notify Service | Consumer | `booking-events` | Читает оба типа, различает по полю `eventType` |
| Analytics Service *(не реализован в MVP)* | Consumer | `booking-events` | Задел на будущее: тот же топик может читать сервис аналитики для сбора метрик (см. Epic 6), не требуя изменений в Booking Service — это и есть преимущество слабой связанности через Kafka |

---

## 5. Гарантии доставки и обработка ошибок

**At-least-once delivery:** Kafka гарантирует, что сообщение будет доставлено
консьюмеру **как минимум один раз** - но в редких случаях (например, при сбое сети
после обработки, но до подтверждения offset) сообщение может быть доставлено повторно.

**Следствие для Notify Service:** обработка событий должна быть **идемпотентной** -
то есть повторная обработка одного и того же `booking.confirmed` не должна привести
к отправке пользователю двух одинаковых SMS. Практическое решение: хранить в БД
Notify Service список уже обработанных `bookingId + eventType` и пропускать дубли.

*(Это открытый момент для обсуждения с разработчиками при реализации - фиксирую здесь,
как это принято в реальной документации: не всё должно быть решено на этапе анализа,
но должно быть явно обозначено.)*
